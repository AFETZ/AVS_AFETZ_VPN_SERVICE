# OpenFlux: отдельный тест AFZVPN

Проверяемая версия: [`a8a8937c59fbb275603bd53e150ecaf46e92148e`](https://github.com/p1neappleXpress/OpenFlux/tree/a8a8937c59fbb275603bd53e150ecaf46e92148e).
Транспорт первого теста — Яндекс Документы (старый редактор, отдельный пустой
документ с редактированием по ссылке). Документ используется для передачи
сообщений курсора. URL хранится в `.env`, а не в репозитории.

## Что добавлено в бот

`OPENFLUX_ENABLED=True` включает отдельную кнопку **«Обход БС · OpenFlux (тест)»**
в главном меню администратора и явно приглашённых участников.
`OPENFLUX_ALLOWED_USER_IDS` — список Telegram ID участников через запятую;
пустой список оставляет доступ только администраторам, включая `BOT_DEV_ID`.
Эта настройка не даёт административных прав или обычную VPN-подписку.
`OPENFLUX_DOC_URL` задаёт документ клиента. Каждый callback повторно проверяет
флаг, доступ Telegram ID и личный чат владельца.
Настройка документа не означает, что выходной узел работает: интерфейс предлагает
проверить соединение, а не объявляет его готовым.

Основная подписка `/sub`, оба существующих `/wl` и `/wl-filtered`, парсер источников,
3X-UI, тарифы, оплаты и записи подписок не участвуют в OpenFlux. Миграция БД не нужна.
Отключение эксперимента — `OPENFLUX_ENABLED=False` и пересоздание только контейнера бота.

Список участников открывает существующий общий тестовый профиль. В этой версии
нет коммерческой многопользовательской выдачи OpenFlux и отзыва доступа по окончании
оплаты. Знание URL даёт доступ к каналу, а upstream использует один виртуальный IP
клиента. Поэтому с общим профилем тестируют по очереди, по одному клиенту.
Удаление ID из списка после пересоздания бота закрывает меню и дальнейшую выдачу,
но не отключает уже сохранённый профиль: для этого нужно заменить документ на
выходном узле и у оставшихся участников либо остановить узел.
Для публичного запуска нужны отдельные сессии/аутентификация, отзыв доступа,
квоты и проверка изоляции клиентов.

## Клиенты

Для сборки нужен Go не ниже указанного в upstream `go.mod` (1.26.4).
Проверяемый toolchain — Go 1.26.8. Сборка из исходников, без запуска бинарника из Git:

```bash
bash scripts/build_openflux_clients.sh
```

`OPENFLUX_GO`, `OPENFLUX_BUILD_DIR`, `OPENFLUX_OUTPUT_DIR` позволяют указать пути.
Архивы Windows/Linux x64 и SHA256SUMS размещаются в `app/data/openflux`, который
уже смонтирован в бот как каталог данных. Бот предлагает скачать существующий
архив; исходники закреплённой версии и уведомления лицензий включены в архивы.
Клиент слушает только `127.0.0.1:1080` и запускается пользователем на своём устройстве.

К закреплённому исходнику применяется `deploy/openflux/patches/client-and-retry.patch`:
пауза 2 секунды между переподключениями Яндекса и отдельная Windows-сборка
`-tags openflux_client`, которая не загружает WinDivert DLL/драйвер для SOCKS-клиента.
Изменённый исходник и patch находятся в архивах. Windows-бинарник собран для x64;
запуск на настоящей Windows-машине требуется проверить отдельно.

Happ не запускает транспорт OpenFlux через обычную ссылку подписки. Для настольного
теста нужен SOCKS5 в браузере. Upstream передаёт TCP/IPv4, не UDP/IPv6; имя назначения
разрешается через DNS на устройстве. Даже с `socks5h` у curl DNS не переносится
на VPS: доменное имя принимает OpenFlux-клиент и вызывает локальный resolver.
Отдельного сквозного шифрования поверх транспорта в просмотренном Yandex backend
нет; для тестовых запросов использовать HTTPS. В закреплённом upstream мобильного
VPN-приложения нет; для AFZVPN отдельно разработаны Android-клиент и проект iPhone
в `mobile/openflux/`. Мобильная версия использует системный VPN-интерфейс, а DNS
совместимых системных resolver'ов переводится на TCP внутри туннеля.

## Выходной узел на VPS

На VPS с установленными Docker Engine и Compose скопировать каталог
`deploy/openflux` в отдельный каталог, например `/opt/afz-openflux`.
Создать там `.env` из `.env.example`, заполнить тот же `OPENFLUX_DOC_URL` и задать
`chmod 600 .env`. Секреты/токены MAX из других приложений не нужны.

```bash
docker compose -f compose.yml config --quiet
docker compose -f compose.yml build
docker compose -f compose.yml up -d
docker compose -f compose.yml ps
docker compose -f compose.yml logs --tail=30 exit
```

У контейнера отдельная bridge-сеть, нет опубликованных портов, host networking,
privileged-режима и общих volumes с основным VPN. `NET_RAW` и `NET_ADMIN` нужны
для raw TCP и правила RST **внутри контейнера**. Копировать RST-команду из README
upstream в firewall хоста нельзя: она относится ко всем TCP-службам хоста.
Ограничены память, CPU, число процессов и размер логов; доступ к частным подсетям
из контейнера закрыт. Docker сам создаёт обычные правила bridge/NAT на хосте.

Статус `running` проверяет только процесс. Для проверки транспорта запустить
клиент на отдельном устройстве с тем же документом, отключить основной VPN на
время теста и выполнить:

```bash
curl --proxy socks5h://127.0.0.1:1080 --max-time 45 https://example.com/
```

Проверить адрес выхода доверенным сервисом — должен совпасть с адресом VPS.
Затем повторить запрос из сети оператора в момент действия белых списков.
Работа через обычный интернет не доказывает работу при БС; нужны также DNS и
доступность фактического WebSocket-хоста редактора, а не только `disk.yandex.ru`.
Одновременно использовать один тестовый клиент и один выходной узел.

Откат выходного узла: `docker compose -f compose.yml down` из его отдельного
каталога. Основные службы VPN и firewall хоста вручную не перезапускаются.

## Управление установленным узлом

На VPS, из `/opt/afz-openflux`:

```bash
docker compose -f compose.yml ps
docker compose -f compose.yml logs --tail=30 exit
docker compose -f compose.yml restart exit
```

Остановка эксперимента: `docker compose -f compose.yml down`.
Повторный запуск: `docker compose -f compose.yml up -d --no-build --pull never`.
Пакет содержит готовый образ, поэтому `docker compose build` в этом каталоге
не используется. В `.env` хранится тот же закрытый тестовый документ, что и в боте;
каталог доступен только root, режим файла — 600.

Для проверки на устройстве открыть в `@AFZVPN_bot` кнопку администратора
**«Обход БС · OpenFlux (тест)»**, выбрать Windows или Linux, скачать архив и
выполнить показанную команду. В браузере указать SOCKS5 `127.0.0.1:1080`.
Для проверки БС использовать сеть нужного оператора и отключить основной VPN
на тестовом устройстве. До включения OpenFlux проверить недоступность тестового
HTTPS-сайта напрямую, затем проверить тот же сайт через SOCKS и адрес выхода VPS.
Сохранить оператора, время и результаты — успешный тест в обычном интернете
сам по себе обход БС не подтверждает.

## Мобильные клиенты AFZVPN

В меню OpenFlux добавлены отдельные Android и iPhone. Android APK подписан,
содержит arm64/x86_64 и рассчитан на Android 8+. Приложение запрашивает системное
разрешение VPN, импортирует отдельный `afz-openflux.json` из бота и управляется
кнопками подключения/отключения. Root и настройка браузерного SOCKS не нужны.
Профиль выдаётся администратору или приглашённому участнику в личном чате, с повторной проверкой доступа
на каждом callback; в бинарник и архив исходников URL документа не встроен.

Для iPhone подготовлены интерфейс приложения, Packet Tunnel Provider,
общее Go-ядро и сценарий подготовки Xcode-проекта. Подписанная IPA пока не собрана:
требуются Mac/Xcode и подпись Apple с разрешением NetworkExtension.
Раздел iPhone в боте явно сообщает об этом и предлагает профиль/исходники.

Подробности, ограничения UDP/IPv6 и команды сборки:
[`mobile/openflux/README.ru.md`](../mobile/openflux/README.ru.md).
Общее мобильное ядро прошло интеграционный тест с настоящим TUN-интерфейсом
в отдельном Linux namespace: системный DNS, HTTPS 200 и выход через
`193.222.97.141`. Android APK прошёл проверку подписей v2/v3 и выравнивания
для страниц 16 KiB. 111 целевых тестов бота прошли, ещё 62 проверки OpenFlux
выполнены на подготовленном рабочем образе с мобильными обработчиками.
После обновления бота все пять проверяемых HTTP-маршрутов отвечают 200.
Проверка запуска Android-приложения остаётся открытой: локальный эмулятор
не смог стабильно запустить Android на имеющемся сервере. Реального телефона
для проверки не было; iOS-проект с Apple SDK ещё не собирался.
Результаты мобильной работы: `.ops/openflux-mobile-20260911/`.

### Импорт по кнопке из Telegram, версия 0.1.1

В меню телефона и под APK/JSON добавлены «Добавить в AFZ OpenFlux» и
«Скопировать настройки». APK 0.1.1 подписан прежним ключом и устанавливается
поверх версии 0.1.0. Android обрабатывает `afzopenflux://import` при запуске
и в уже открытом приложении, проверяет и сохраняет профиль. Кнопка
«Вставить из буфера» позволяет обойти ограничения браузера Telegram.
Файл JSON для обычного подключения больше не требуется.

HTTPS-страница работает через существующий `/connection?client=openflux`,
получает профиль из fragment и открывает приложение. Fragment не передаётся
HTTP-серверу; страница не выдаёт профиль из конфигурации и не загружает сторонние
ресурсы. Если автоматический переход заблокирован браузером, остаётся явная
кнопка открытия приложения. Существующие перенаправления Happ сохраняются.

iOS-исходники получили URL scheme, сохранение профиля и импорт из буфера.
Готовой подписанной iOS-сборки по-прежнему нет. Переход из Telegram на реальном
телефоне требует проверки. Результаты и откат: `.ops/openflux-import-20260911/`.

## Приглашённые участники и масштабирование

Для добавления участника обновить `OPENFLUX_ALLOWED_USER_IDS` в `.env` и
пересоздать только бот: `docker compose up -d --no-deps --no-build bot`.
Участник открывает личный чат с ботом и отправляет `/start` или нажимает «Меню»:
появляется «Обход БС · OpenFlux (тест)». Административные права не выдаются.

Для нескольких одновременно подключённых устройств в текущем ядре нужен
отдельный документ и отдельный изолированный экземпляр выходного узла на каждое
устройство. Контейнеры можно размещать на одном VPS; отдельный сервер каждому
пользователю не требуется. Боту потребуется хранить соответствие Telegram ID,
устройства, документа и контейнера и выдавать персональный профиль. Пока такой
учёт и автоматическое создание экземпляров не реализованы.

Для массового сервиса нужны аутентификация пользователей/устройств, адресация
независимых сессий, шифрование поверх транспорта, отзыв ключей, квоты и
автоматическое распределение по выходным узлам. Замены виртуального IP
недостаточно: Yandex backend принимает данные общего документа без разделения
получателей. Одна постоянная ссылка подписки на пользователя возможна как
интерфейс выдачи настроек; внутри нужны независимые сессии устройств.
Вместимость VPS и пропускную способность транспорта определять нагрузочным
тестом с целевым числом одновременных клиентов и сетями операторов.
